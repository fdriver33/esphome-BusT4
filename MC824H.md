# MC824H support and hardware validation

This document describes the MC824H/MCA1R10 work added to this fork of `esphome-BusT4`, including the protocol findings, position handling, controller-backed switches and numbers, corrected register map, and real-hardware validation.

The implementation was tested on a Nice **MC824H / MCA1R10** control unit with product string `MC824H`. The tested installation uses one active motor on **M2 / ENC2**.

## Summary of changes

Two main groups of changes were added:

1. **MC824H indexed encoder position support**
   - explicit indexed GET requests
   - correct 16-bit position decoding
   - correct programmed open/closed scaling
   - physical encoder maximum kept separate from the 100% reference
   - MC824H-specific endpoint behavior
   - MC824H-specific handling of `INF_IO`

2. **Controller-backed configuration entities**
   - native Bus-T4 switch entities with GET readback
   - native Bus-T4 number entities with GET readback
   - corrected MC824H configuration register addresses
   - corrected opening/closing speed register addresses
   - SET followed by GET verification
   - periodic synchronization with changes made outside Home Assistant

# 1. MC824H indexed encoder support

## Problem

A normal unindexed `04/11` GET is not sufficient for reliable MC824H live position selection. The controller can return an indexed 3-byte payload and can remember a previously selected channel.

For MC824H, position reads therefore need an explicit selector/index byte.

## Indexed GET format

A normal DMP GET uses:

```text
99 00 00
```

An indexed GET uses:

```text
99 00 01 <index>
```

For the tested MC824H installation, the active encoder is requested with:

```text
index = 0x01
```

The corresponding position response payload is:

```text
[index] [MSB] [LSB]
```

Example:

```text
01 0B 12
```

means:

```text
index = 0x01
position = 0x0B12 = 2834
```

The component validates the selector on MC824H replies and ignores a 3-byte position response when its selector does not match the expected MC824H index.

## Why index `0x01`?

O-View Bus-T4 captures identify selector `0` and selector `1` as separate motor channels. On the tested installation, selector `0x01` matches the physically connected **M2 / ENC2** channel and returns the live encoder value.

The implementation therefore currently uses:

```cpp
MC824H_POSITION_INDEX = 0x01;
```

This is a protocol/device-specific choice, not an encoder endpoint value.

# 2. MC824H position register map

The following registers were confirmed on real hardware using indexed selector `0x01`:

| Device/Register | Meaning | Tested value | Component use |
|---|---|---:|---|
| `04/11` | Current/live encoder position | changes continuously | live position |
| `04/12` | Physical maximum encoder position | `2932` | diagnostics/physical maximum |
| `04/13` | Programmed closed reference | `0` | 0% reference |
| `04/18` | Programmed open reference | `2832` | 100% reference |
| `04/19` | Alternate minimum position | unsupported on tested MC824H | not used |

The values `0`, `2832`, and `2932` are **measurements from one installation only**. They are not compiled into the component.

At startup the component reads the actual values from each controller.

## Important distinction: `04/12` vs `04/18`

The physical encoder limit (`04/12`) is not necessarily the programmed open point (`04/18`).

On the tested unit:

```text
04/12 physical maximum = 2932
04/18 programmed open  = 2832
```

Using `2932` as 100% would make the gate show only about 96.6% at its programmed fully open position.

The corrected implementation keeps these separate:

```text
encoder_max_ = 04/12
pos_max_     = 04/18
```

For MC824H, `04/12` is never allowed to replace a valid programmed `04/18` open reference.

# 3. Dynamic position calculation

Position is calculated using the programmed closed and open references:

```text
position = (current - closed_reference) / (open_reference - closed_reference)
```

The implementation uses signed-safe floating-point arithmetic before clamping:

```cpp
const float span = static_cast<float>(pos_max_) - static_cast<float>(pos_min_);
float pos = (static_cast<float>(encoder_pos) - static_cast<float>(pos_min_)) / span;
pos = std::max(0.0f, std::min(1.0f, pos));
```

This also avoids unsigned underflow if a live encoder sample temporarily falls below the programmed closed reference.

## Example using the tested controller

```text
closed = 0
open   = 2832
current = 1203
```

then:

```text
1203 / 2832 = 42.48%
```

If another MC824H reports:

```text
closed = 0
open   = 2932
```

that installation automatically uses `2932` as its 100% reference.

A non-zero closed reference is also supported. For example:

```text
closed = 100
open   = 3000
```

uses:

```text
(current - 100) / (3000 - 100)
```

# 4. Endpoint behavior while moving

The MC824H encoder can reach or slightly pass the programmed endpoint before the controller changes its movement status to fully Opened or Closed.

The component therefore prevents a contradictory UI state.

While the controller still reports opening:

```text
normalized >= 100% -> publish 99%
```

While the controller still reports closing:

```text
normalized <= 0% -> publish 1%
```

When the controller reports the final state:

```text
Opened -> 100%
Closed -> 0%
```

On the tested unit the live encoder was approximately:

```text
fully open: around 2834
programmed open reference: 2832
fully closed after settling: around 4-6
programmed closed reference: 0
```

This is why the controller state remains authoritative at the exact endpoints.

# 5. Initialization changes

MC824H is detected from the product name prefix:

```text
MC824H...
```

This also allows related product strings beginning with the same prefix to enter MC824H mode.

During initialization, MC824H uses indexed reads for:

```text
04/18 programmed open reference
04/13 programmed closed reference
04/12 physical encoder maximum
```

After the endpoint registers are known, initialization immediately primes the live encoder with indexed:

```text
04/11 current position
```

The startup log identifies the mode, for example:

```text
Product: MC824H
Mode: MC824H (indexed 16-bit encoder, index 0x01)
Position source: Encoder (primary)
```

# 6. `INF_IO (0xD1)` handling

The generic Bus-T4 code contains a limit-switch mapping for `INF_IO` that is useful on other controller families.

The exact MC824H `D1` layout has not been proven to use the same semantics. Applying the generic mapping could therefore falsely force the cover to fully open or fully closed.

For MC824H, the generic limit-switch mapping is disabled:

```text
MC824H INF_IO -> left raw / not interpreted as generic limit switches
```

Final Opened/Closed state is instead taken from the controller status plus the validated encoder position.

# 7. Partial-open positions

The partial-open command itself does not contain a percentage. The target positions are stored in the control unit.

Observed MC824H registers:

| Register | Meaning |
|---:|---|
| `04/1B` | Partial Open 1 position |
| `04/1C` | Partial Open 2 position |
| `04/1D` | Partial Open 3 position |

On the tested installation:

```text
04/1B index 0x01 = 2832
04/18 index 0x01 = 2832
```

Therefore `CMD_OPEN_PARTIAL_1` opened the gate fully: Partial Open 1 was configured to the same position as full open.

The component currently sends Partial Open 1/2/3 commands but does not yet expose `04/1B-04/1D` as native editable number entities.

# 8. Corrected Level 1 configuration register map

The previous contiguous assumption `0x80-0x85` was incorrect.

The register map was cross-checked against the working `esphome-nice-bidiwifi` implementation and then tested on MC824H hardware.

Correct switch registers:

| Function | Register | YAML setting |
|---|---:|---|
| L1 Auto-Close | `0x80` | `auto_close` |
| L2 Close after Photo | `0x84` | `photo_close` |
| L3 Always Close | `0x88` | `always_close` |
| L4 Standby | `0x8C` | `standby` |
| Peak | `0x93` | `peak` |
| L6 Pre-Flash | `0x94` | `pre_flash` |

Important examples of why contiguous mapping was wrong:

```text
0x81 = Auto-Close Pause Time
0x85 = Photo-Close Time
0x89 = Always-Close Time
```

Those are numeric timing parameters, not boolean switches.

## Peak `0x93`

The component register map contains `0x93` for Peak because it exists in the reference implementation. The tested MC824H rejected this register, so Peak is not included in the example configuration.

Treat Peak as controller-dependent until separately verified on another control unit.

# 9. Controller-backed switches

A new native ESPHome switch platform was added:

```yaml
switch:
  - platform: bus_t4
    name: "L1 Auto-Close"
    bus_t4_id: bus
    cover_id: gate
    setting: auto_close
```

Supported settings:

```text
auto_close
photo_close
always_close
standby
peak
pre_flash
```

## Switch synchronization behavior

The switch does not use an optimistic state.

At startup:

1. resolve the discovered controller address from the associated cover
2. send GET for the configuration register
3. wait for a successful DMP GET response
4. publish `OFF` for zero, `ON` for any non-zero value

If no valid initial state has been received, GET is retried every 2 seconds.

After a valid state exists, the switch refreshes every 60 seconds.

When Home Assistant changes a switch:

1. send SET with one byte `00` or `01`
2. do not publish the requested value optimistically
3. immediately send GET
4. publish only the value returned by the controller

This keeps Home Assistant synchronized even when the controller rejects or changes a requested value.

## SET and GET payload form

Boolean SET payload:

```text
04 <register> A9 00 01 <00|01>
```

GET payload:

```text
04 <register> 99 00 00
```

SET acknowledgements are ignored for entity state. The state comes from the following GET response.

# 10. Controller-backed number entities

A native ESPHome number platform was also added.

Supported parameters:

| Function | Register | YAML setting | Range | Step |
|---|---:|---|---:|---:|
| Opening Speed | `0x42` | `opening_speed` | 1-100 | 1 |
| Closing Speed | `0x43` | `closing_speed` | 1-100 | 1 |
| Auto-Close Pause Time | `0x81` | `pause_time` | 0-250 s | 5 s |
| Photo-Close Time | `0x85` | `photo_close_time` | 0-250 s | 1 s |
| Always-Close Time | `0x89` | `always_close_time` | 0-250 s | 1 s |

Example:

```yaml
number:
  - platform: bus_t4
    name: "Opening Speed"
    unit_of_measurement: "%"
    mode: slider
    bus_t4_id: bus
    cover_id: gate
    setting: opening_speed
```

The number entities use the same synchronization model as the switches:

```text
startup GET
SET on user change
immediate GET readback
2 s retry until first valid read
60 s periodic refresh
```

Only the controller readback is published.

## Corrected speed registers

The opening/closing speed constants were corrected to:

```text
Opening Speed = 0x42
Closing Speed = 0x43
```

The older `0x91/0x90` mapping was not correct for this controller/register set.

# 11. Hardware validation results

The following behavior was confirmed from real MC824H Bus-T4 traffic.

## Position

| Test | Result |
|---|---|
| indexed `04/11` current position | PASS |
| indexed `04/12` physical maximum | PASS |
| indexed `04/13` closed reference | PASS |
| indexed `04/18` open reference | PASS |
| full CLOSED -> OPEN cycle | PASS |
| full OPEN -> CLOSED cycle | PASS |
| dynamic 0-100% calculation | PASS |
| Opened/Closed final endpoint state | PASS |

A complete closing capture showed the encoder decreasing continuously from the open range down to zero before the controller later confirmed Closed.

## Configuration switches

| Register | Function | GET | SET |
|---:|---|---|---|
| `0x80` | Auto-Close | PASS | PASS (OFF tested) |
| `0x84` | Photo-Close | PASS | not separately toggled during validation |
| `0x88` | Always Close | PASS | PASS ON + OFF |
| `0x8C` | Standby | PASS | not separately toggled during validation |
| `0x94` | Pre-Flash | PASS | not separately toggled during validation |
| `0x93` | Peak | rejected on tested MC824H | not used |

The successful `0x88` test verified both directions:

```text
SET ON -> GET -> 0x01 -> Home Assistant ON
SET OFF -> GET -> 0x00 -> Home Assistant OFF
```

## Number parameters

All five number registers were hardware tested with both SET and GET readback:

| Register | Function | Result |
|---:|---|---|
| `0x42` | Opening Speed | SET + GET PASS |
| `0x43` | Closing Speed | SET + GET PASS |
| `0x81` | Auto-Close Pause Time | SET + GET PASS |
| `0x85` | Photo-Close Time | SET + GET PASS |
| `0x89` | Always-Close Time | SET + GET PASS |

Examples from the hardware test included:

```text
Opening Speed       -> 53 -> readback 53
Closing Speed       -> 27 -> readback 27
Auto-Close Pause    -> 60 -> readback 60
Photo-Close Time    -> 6  -> readback 6
Always-Close Time   -> 6  -> readback 6
```

# 12. Migration from old optimistic YAML

Older configurations used template switches such as:

```yaml
switch:
  - platform: template
    name: "Auto-Close"
    optimistic: true
    turn_on_action:
      - lambda: id(gate).set_auto_close(true);
    turn_off_action:
      - lambda: id(gate).set_auto_close(false);
```

This changes the controller but does not read its actual state after boot or after a rejected write.

Replace it with:

```yaml
switch:
  - platform: bus_t4
    name: "Auto-Close"
    bus_t4_id: bus
    cover_id: gate
    setting: auto_close
```

The old C++ methods remain available for compatibility, but native Bus-T4 entities are recommended for Home Assistant.

Similarly, raw/template number entities can be replaced with the new native number platform where a named setting is supported.

# 15. Known limitations / future work

- selector `0x01` is the verified active M2/ENC2 channel on the tested MC824H setup; multi-motor/channel selection is not currently exposed as YAML configuration
- Partial Open positions `04/1B-04/1D` are known/readable but not yet exposed as native editable number entities
- Peak register `0x93` was rejected by the tested controller and remains controller-dependent
- exact MC824H `INF_IO/D1` bit semantics remain intentionally unimplemented rather than guessed
- configuration entities currently send every requested value; rapid slider movement can queue intermediate SET/GET operations rather than using a debounce/latest-value-wins strategy

These limitations are deliberate where the protocol behavior has not yet been proven on hardware.
